# Сценарий защиты MiniDB

## Подготовка

Из корня проекта выполните:

```sh
python3 -m unittest discover -s tests -v
python3 demo.py
```

Ожидается: 41 тест OK, затем сообщение «Проверка пройдена».
Семь сообщений `Ошибка:` в демонстрации ожидаемы: они показывают защиту PK/FK.
Автоматическая демонстрация работает во временной базе и не меняет `data/sample`.

## Ручной показ (5-7 минут)

Для каждого полного повтора нужна новая база. Один раз выполните:

```sh
python3 seed.py data/defense
python3 main.py
```

Если папка `data/defense` уже есть, генератор откажется её перезаписывать.
Выберите другую новую папку и замените путь в командах `open` обоих сеансов.

### Сеанс 1

Вводите команды из `docs/demo_session1.txt` по порядку.

| Шаг | Что показать | Ожидается |
| --- | --- | --- |
| Открытие и SELECT | Три связанные таблицы | 5 datasets, 5 models, 20 experiments |
| CREATE notes | Собственная схема таблицы | Таблица создана |
| INSERT notes/datasets/models | Строки с пробелами, авто-ID | notes=1, dataset=6, model=6 |
| INSERT_MANY models | Пакет без ручных ID | Добавлено 2 записи, ID 7 и 8 |
| INSERT experiments | Ссылки на dataset=6, model=6 | ID эксперимента 21 |
| SELECT accuracy >= 0.9 | Числовая фильтрация | Только эксперимент 21 |
| UPDATE status/name | Изменение строки и датасета | По 1 изменённой записи |
| DELETE experiment 20 | Удаление с фильтром | Удалена 1 запись; SELECT даёт 0 |

Затем идут **семь заведомо неверных операций**:

1. Модель с ID=1: ошибка дублирования PRIMARY KEY.
2. Эксперимент с dataset_id=999: неверный FK.
3. Эксперимент с model_id=999: неверный FK.
4. UPDATE experiment 21 на dataset_id=999: неверный FK, прежняя ссылка остаётся.
5. DELETE dataset 6: запрещено из-за experiment 21.
6. UPDATE model 6 на ID=60: запрещено из-за experiment 21.
7. DELETE model 6: запрещено из-за experiment 21.

Программа продолжает принимать команды. Выполните `exit`.

### Сеанс 2 - новый процесс

Запустите `python3 main.py` снова и введите команды из `docs/demo_session2.txt`.

Проверьте:

- таблица notes сохранилась и содержит одну запись;
- dataset 6 называется «Обновлённый датасет»;
- model 6 существует с прежним ID;
- experiment 21: dataset_id=6, model_id=6, accuracy=0.95, status=completed;
- SELECT experiment 20 возвращает 0 записей;
- общее число экспериментов равно 20: 20 исходных + 1 новый - 1 удалённый.

Это подтверждает сохранение схемы, INSERT, UPDATE и DELETE после перезапуска,
а также отсутствие изменений от ошибочных операций. Завершите `exit`.

## Автоматическое воспроизведение этих же команд

`python3 demo.py` читает те же два файла команд, подставляет временную папку,
запускает два процесса и проверяет конечное состояние файлов. Вывод последнего
контрольного запуска сохранён в `docs/demo-output.txt`.

## Что объяснить на защите

Схемы и данные хранятся в собственных UTF-8/CSV файлах, без готовой СУБД.
Все проверки выполняются до замены файла; связи фиксированы в Python.
Поиск последовательный, запись перезаписывает таблицу. Авто-ID вычисляется от
текущего максимума; после удаления максимального ID возможен повтор его номера.
Диаграмма приведена в отчёте, исходник DBML находится в `docs/schema.dbml`.
Индекс, benchmark, JOIN и backup/restore в текущую версию не входят.
